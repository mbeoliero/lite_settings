# 决策记录

记录已定型方案背后的取舍与被否决的备选。技术方案本身见 [design/](design/README.md)。

每条格式：**决策** / **理由** / **否决的备选** / **后果**。

---

## D1. 存储选用 MySQL 与 PostgreSQL

**决策**：同时支持 MySQL 与 PostgreSQL，通过 `Dialect` 接口抽象差异。

**理由**：DB 直连模式要求多个业务实例并发访问同一份数据，需要成熟的多连接并发模型；两者都是既有基础设施，运维备份体系现成。

**否决的备选**

| 备选 | 否决理由 |
|---|---|
| SQLite 内嵌 | 最轻，但文件锁模型不适合多实例并发访问，与 DB 直连模式的核心场景冲突 |
| etcd | 自带 watch 与分布式一致性，但属重量级依赖，与"极简"目标冲突 |
| 文件 + Git | 极轻且版本能力免费，但并发写与后续 UI 编辑体验差 |

**后果**：需维护双方言的建表语句、UPSERT 语法、revision 自增语句，测试矩阵翻倍。差异集中在 `Dialect` 的三个方法内，可控。

## D2. 变更感知采用 prefix 全量拉取，不做 key 级增量

**决策**：watch 单位为 prefix。水位变化后全量拉取整个 prefix 并本地整组替换，不存在 `WHERE revision > N` 的增量查询。

**理由**：容错等级差异是决定性的。

- 增量模式下漏掉一次通知 = **该条变更永久丢失**
- 全量模式下漏掉一次通知 = **延迟一个轮询周期**，下一轮自动修正

因为每次拉取都是自洽的完整快照。此外该模型与 Apollo 一致 —— Apollo 客户端长轮询获得 `notificationId` 后全量拉取整个 namespace，同样不做 key 级 diff。本项目的 prefix 对应 Apollo 的 namespace。

**否决的备选**：按 revision 增量拉取。除容错问题外，还需要 `lite_config.revision` 列及其索引、`Store.Since()` 接口，并强制采用软删除以传播删除事件。

**后果**

- 连带砍掉：`lite_config.revision` 列与索引、`Since()` 接口、软删除与墓碑清理 job
- 任一 key 变更会推高全局 revision，导致所有客户端重拉各自的 prefix。配置变更低频、单组数据量小，该放大可接受

## D3. 全局水位用单行表的行锁维护，不用 advisory lock

**决策**：`lite_config_meta` 单行表，写事务首条语句为 `UPDATE lite_config_meta SET revision = revision + 1 WHERE id = 1`。

**理由**：这条语句同时完成两件事 —— 行级排他锁持有至 commit（串行化写入），以及生成水位号码。

**否决的备选**

**PostgreSQL Advisory Lock**：它提供串行化，但不提供号码。水位必须持久化，因此仍需要一张表存 `revision` —— 表一张都没省掉，只是把行锁替换成另一种锁。此外：

- MySQL 无对等物。`GET_LOCK()` 是连接级命名锁，语义与生命周期均不同；两库都支持意味着两套机制、两套测试。行锁两库语义一致。
- `pg_advisory_lock` 不随事务释放，连接池复用下遗漏 unlock 即产生卡死的锁。行锁随 commit/rollback 自动释放。
- `pg_advisory_xact_lock` 可避免泄漏，但前两条仍成立。

**用 `MAX(id) FROM lite_config_history` 或自增主键作水位**：并发事务下自增 id 可能乱序可见。事务 A(id=5) 与 B(id=6)，B 先提交 —— 客户端读到水位 6 并拉取（此时 A 未提交，拉取不到），随后 A 提交，水位仍为 6，客户端判定无变化，**A 的改动被永久跳过**。

**后果**：写入被串行化。配置写入是人工低频操作，无实际影响。

## D4. `version` 只存于 history 表

**决策**：`lite_config` 不含 `version` 列。写入时执行 `MAX(version)+1 FROM lite_config_history WHERE config_key = ?`。

**理由**：读路径不关心版本号。写入时多一次索引查询，而写入是人工低频操作。

**否决的备选**：在 `lite_config` 冗余 `version`。唯一有价值的场景是 CAS 发布（`UPDATE ... WHERE version = ?` 防并发覆盖），但配置中心的并发写冲突基本靠人协调，v1 不做。

**后果**：将来需要 CAS 时增加一列即可，属纯增量改动。已列入演进计划优先级 1。

---

## D5. 采用硬删除

**决策**：`DELETE FROM lite_config`，同时向 history 追加 `op='delete'` 记录（含完整 value）。

**理由**：软删的唯一动机是让增量查询能传播删除事件。D2 采用全量拉取后该动机消失 —— 客户端拉到 9 条而本地有 10 条，自行 diff 即可感知删除。

恢复能力未损失：history 中 `op='delete'` 记录保留完整 value，回滚到删除前版本即为恢复。

**后果**

- 砍掉 `deleted` 列、所有查询中的 `WHERE deleted = false`、墓碑清理 job
- `History` 与 `Rollback` 必须以 history 表为准，不得先查 `lite_config` 确认 key 存在（已作为实现约束写入 [design §4.4](design/03-mechanics.md)）

## D6. `Client` 为具体类型，多态置于 `Source` 层

**决策**：`Client`、`Group` 是具体 struct；`Source` 是接口，两种接入模式各实现一份。

**理由**：Go 1.27 规定"接口方法不能声明类型参数，泛型方法也不能实现接口方法"。要在 `Client` 上使用泛型方法（`c.Get[T](key)`），`Client` 就不能是接口。

**否决的备选**

- **`Client` 设计为接口**，两种模式各实现一份：与泛型方法直接冲突。
- **保留泛型函数形式** `lite.Get[T](c, key)`：Go 1.18 起即可用，无需 1.27。但调用侧啰嗦，且标量取值与结构体反序列化无法统一入口。

**后果**：多态收敛在一个约 30 行的 `Poll` 实现上，两种模式共享缓存、Watch 回调、重试与冷启动兜底逻辑。

## D7. 严格解码默认关闭

**决策**：`json/v2` 的 `RejectUnknownMembers` 通过 `WithStrictDecode()` 显式开启，默认关闭。

**理由**：默认开启会在滚动发布期间造成事故 —— 为服务新版本增加配置字段后，尚在运行的旧实例不认识该字段，严格模式下整份配置解析失败，旧实例无法加载配置。

**否决的备选**：默认开启。捕获配置字段拼写错误（如 `timeuot`）确有价值，但代价是破坏滚动发布这一常规操作。

**后果**：字段拼写错误默认静默为零值。需要严格性的场景显式开启即可。

## D8. 直接依赖 `gopkg.in/yaml.v3`

**决策**：`client` 包的外部依赖为 `gopkg.in/yaml.v3`（其自身零传递依赖）。

**理由**：`encoding/json/v2` 已进入标准库，但不覆盖 yaml，而配置 Value 需支持 yaml 格式。

**否决的备选**：将 yaml 解码做成可插拔子包（`import _ ".../client/yamlfmt"` 注册），使 `client` 保持纯标准库。以一个零传递依赖换取"忘记 import 即运行时报错"的陷阱，不划算。

**后果**：`client` 依赖 = 标准库 + yaml.v3。

## D9. 仅 `cmd/lsctl` 独立成 module

**决策**：`cmd/lsctl` 拥有自己的 `go.mod`；`client` 暂不拆分，与 `store`、`server` 同处根 module。

**理由**

`cmd/lsctl` 是叶子（main 包，无人 import），**给叶子独立 module 是成本最低的拆法** —— 不涉及任何 import path 变化，不影响 SDK 使用者。它引入的 cobra 与 bubbletea 全家桶因此完全隔离在根 module 之外。

`client` 不拆的理由：

- 拆分随时可做且**不改 import path**，只是该目录多一个 `go.mod` 文件
- Go 1.17+ 的 module graph pruning 使得"依赖污染"主要是观感问题 —— 不下载源码、不进二进制，仅在 module graph 中多几行
- 提前拆分需承担双 tag 发版、CI 双跑、版本双轨（"client v1.2 配 server v0.9 是否兼容"）的长期成本

**否决的备选**

- **全部单 module**：bubbletea 全家桶进入所有 SDK 使用者的 module graph。既然叶子拆分零成本，无理由容忍。
- **`client` 一并拆分**：属过早优化，触发信号尚未出现。

**后果**

- 需要 `go.work` 支撑本地跨 module 开发（免去 `replace` 指令）
- CI 需覆盖两个 module
- 触发 `client` 拆分的信号：`server` 引入重依赖，或有外部团队接入需要独立版本承诺

---

## D10. lsctl 使用 cobra

**决策**：`lsctl` 用 cobra 而非标准库 `flag`。

**理由**：D9 使 lsctl 独立成 module 后，"极简依赖"的约束不再作用于它。cobra 换来 shell 补全与统一的 help 输出，并省去约 100 行手写子命令分发。

**否决的备选**：标准库 `flag` + 手写分发。在依赖已被隔离的前提下，其唯一优势（零依赖）不再产生收益。

## D11. TUI 与非交互命令同属一个二进制

**决策**：单一 `lsctl` 二进制，`lsctl ui` 进入 TUI。

**理由**：两个二进制（`lsctl` + `lsui`）是更差的 UX —— 用户需记住两个命令名，且共享的连接参数需配置两遍。

**否决的备选**：TUI 独立二进制。

**附带约束**：TUI 是加法而非替代，每个 TUI 操作必须存在等价的非交互命令，否则 CI/CD 不可用。

---

## D12. 不做命名空间与多环境

**决策**：一个环境一套数据库，服务本身不感知环境概念。`config_key` 全局唯一。

**理由**：环境隔离由数据库边界天然提供，schema 无需 `env` 列，所有查询、API 与 SDK 初始化均少一个参数。

**否决的备选**

| 备选 | 否决理由 |
|---|---|
| 增加 `env` 列，唯一键为 `(env, key)` | 每个查询、每个 API、每次 SDK 初始化都要多带一个参数 |
| 环境写进 key 前缀（`prod/order-svc/db`） | 单库即可运行，但权限隔离与误操作防护为零 |

**后果**：跨环境配置 diff 需手动对比。

---

## D13. TUI 范围限定为单屏三栏

**决策**：TUI 仅一屏三栏（keys / value / history），不做多屏、多标签、设置页、鼠标支持；编辑委托给 `$EDITOR`。

**理由**

TUI 的价值集中在三个场景，其中回滚是决定性的：

| 场景 | 非交互命令现状 | TUI |
|---|---|---|
| 回滚 | `history` → 肉眼找版本号 → `diff k 3 5` → `rollback --to 3`，三条命令加复制粘贴 | 方向键滚版本，diff 实时渲染于旁栏，回车确认 |
| 发布前 diff | `set -f file.yaml` 盲写 | `$EDITOR` 编辑 → 对比当前值 → 确认 |
| key 浏览 | `list` + grep | 树形浏览 |

回滚是压力操作 —— 线上故障时才回滚，此时减少命令数与复制粘贴的价值最高。

编辑委托 `$EDITOR` 省去整个文本编辑组件，且 YAML 缩进敏感，自制编辑器体验必然差于用户熟悉的编辑器。

**后果**：TUI 工作量约 1.5 天，为独立增量，可推迟或裁剪而不影响其余模块交付。

## D14. 线路格式单独成 `api` 包

**决策**：server 与 client 共用的 JSON 结构放进只依赖 stdlib 的 `api` 包；该包只放数据结构，不放行为。

**理由**

D6 的依赖规则要求 client 不得 import server，但两端必须对同一套 JSON 达成一致。三个去处：

| 方案 | 问题 |
|---|---|
| 放 `server` | 违反 client 不得 import server |
| 放 `store` | 把数据库 driver 拖进纯 HTTP 客户端的依赖图 |
| 各自复制一份 | 是同一个仓库两半之间的协议，复制必然漂移 |

`api` 只依赖 stdlib，因此进不了任何人的依赖负担。

**否决的备选**：让 client 复制结构体定义。四个字段的结构确实抄得动，但线路协议一旦两处定义，改一处忘一处就是线上解析失败，而这类 bug 只在跨版本部署时才暴露。

**后果**：新增一层包。约束"只放数据结构"必须守住——一旦 `api` 开始持有逻辑，两端会通过它重新耦合起来。

## D15. 客户端可见的水位统一取自 revisionWatcher

**决策**：`/v1/configs`、`/v1/watch`、`/v1/revision` 报同一个数字，来源是 revisionWatcher 而非直接查库。revisionWatcher 未完成首轮轮询时才回落到查库。

**理由**

revisionWatcher 落后数据库最多一个轮询周期，这是 §8.1 的设计目的（DB 查询量与客户端数量无关）。若不同端点分别报两个来源的水位，客户端的标准启动流程——`GET /v1/configs` 拿基线，再拿该基线去 `watch`——会因两数不等而立即返回，每次冷启动白跑一轮。

标低不标高是安全方向：数据只会比标签更新，客户端下一轮自动收敛；反过来会让陈旧数据顶着新水位，那次变更被永久跳过。revisionWatcher 的值恒不高于库内真实值，天然满足。

**否决的备选**：让所有端点都查库。这样 watch 的判定基准（revisionWatcher）与客户端的基线（库）仍然是两个来源，错配依旧；且 `/v1/revision` 会变成一个可被高频轮询的数据库查询。

**后果**：写入后 `/v1/revision` 最多滞后一个轮询周期才反映出来。写入响应自身返回事务内的真实 revision，因此审计与"我这次写入拿到几号"不受影响。

## D16. `/healthz` 只做启动门控

**决策**：首轮轮询成功前返回 503，之后恒为 200；数据库的实时状态放在响应体的 `db_error` 字段里，不影响状态码。

**理由**

让 healthz 跟随 DB 状态，会在数据库闪断时把所有实例同时摘掉，连带掐断全部长轮询连接。而这些客户端本可以继续用本地缓存正常工作——配置中心发陈旧配置远好过发不出配置。

只在首轮轮询前报 503，则既避免了实例刚起来就被挂上负载均衡，又不会产生随 DB 抖动的 flapping。

**否决的备选**：拆 `/healthz`（存活）与 `/readyz`（就绪）两个端点。语义更标准，但轻量配置中心的部署形态通常只配一个探针，多一个端点多一份配置错误的机会。

**后果**：数据库长时间不可用时实例仍报健康。这是刻意的——此时把实例摘掉不会让任何客户端更好过。观测应依赖 `db_error` 字段与日志，而非探针。

## D17. 每个测试包落在独立的数据库上

**决策**：`internal/testdb` 按调用方传入的 suffix 派生数据库名，各测试包互不共享库。

**理由**

`lite_config_meta` 是全局单行水位，而 `go test ./...` 默认并行跑各个包。共用一个库时，任何跨包的并发写入都会在别的包眼里表现成 revision 空洞——而那正是 `store` 要断言的核心不变量（D3）。这不是清理数据能解决的：水位本身就是全局共享的。

**否决的备选**：文档要求用 `go test ./... -p 1`。`go test ./...` 是默认动作，让它失败等于交付一个已知会踩的坑；且 CI 里没人会注意到这条要求。

**后果**：测试首次运行会建库，需要建库权限。新增带集成测试的包时必须传一个新的 suffix，忘了传会退回到互相踩的状态。

## D18. `Source.Poll` 收一个 `PollRequest`，用 `nil` 表示无变更

**决策**：`Poll(ctx, PollRequest) (*api.Snapshot, error)`，而非设计初稿的 `Poll(ctx, since int64) (Snapshot, int64, error)`。

**理由**

初稿的 `int64` 返回值是冗余的：`api.Snapshot` 本身就带 `Revision`，两处水位一旦不一致就是 bug 温床。

入参必须携带 prefix、轮询间隔与挂起上限：这些都是 `Client` 侧的 Option（§7.4），却只有 `Source` 用得上。做成位置参数会是四个入参，且以后每加一个选项都要改所有实现；结构体则可以加字段不破坏兼容。

prefix 逐次传入而不是在构造 Source 时固定，还消掉了一个顺序依赖——`lite.HTTP(...)` 与 `WithPrefixes(...)` 谁先谁后都不影响结果。

`nil` 快照表示"时限内无变更"，正好对上 HTTP 的 304，且与 `error` 明确区分开：客户端据此决定要不要退避。若把无变更也做成错误，长轮询每挂满一次就会触发一轮退避。

**否决的备选**：`Poll` 返回 `(snapshot, changed bool, err error)`。多一个返回值，而 `nil` 已经把这件事说清楚了。

**后果**：`Source` 的实现方要记住"没变更返回 `(nil, nil)` 而不是错误"。这条写进了接口文档注释。

## D19. `lite.New` 同步完成首拉，且首拉不触发 `OnChange`

**决策**：`New` 阻塞到第一份快照到手才返回；这份快照不算"变更"，不触发 `OnChange`（`Watch` 在注册时另行同步回调一次）。

**理由**

异步首拉意味着 `c := lite.New(...)` 之后紧跟的 `c.Get` 会读到空快照，取到默认值。这个坑每个用这个 SDK 的人都会踩一次，而且踩中时表现为"配置偶尔不生效"，极难查。

首拉不触发 `OnChange` 则是因为此刻 `New` 还没返回——回调闭包里根本拿不到 client 句柄，想在回调里读别的配置就是空指针。而且"所有 key 都是新的"这条通知没有信息量。真正需要初值的场景由 `Watch` 覆盖：它在注册时同步回调一次，那时句柄已经存在。

**否决的备选**：`New` 不返回 error，把首拉失败留到第一次 `Get`。这会把一个启动期的、应当让进程起不来的故障，伪装成运行期的"配置读不到"。

**后果**：`New` 会阻塞最多 `WithStartupTimeout`（默认 10s）。配置源不可用且没配 `WithFallbackFile` 时进程直接起不来——这是 §10 明确要的行为。

## D20. `server.Start` 与 `Run` 分离

**决策**：新增 `Server.Start(ctx) (stop func())`，只跑水位轮询、不监听端口；`Run` 在其之上加监听。

**理由**

`Handler()` 原本就带着一条警告注释："只用 Handler 而不调用 Run 时 revisionWatcher 不会运行，`/v1/watch` 会一直挂到超时。" 那是个被文档化的坑，不是设计。把配置服务挂到业务已有的 HTTP 栈上是轻量部署的常见形态，这种用法不该只能靠自己复刻 revisionWatcher 的启停逻辑。

`stop` 的顺序也被固定在一处：先 `br.Close()` 释放挂起的长轮询，再取消 ctx 停轮询。`Run` 的优雅退出直接复用它，不再各写一遍——这个顺序写反会把退出拖满一个长轮询周期（见 §8.3）。

**后果**：`Server` 多一个导出方法。`Start` 返回的 `stop` 可重复调用（`sync.Once`），但 `Start` 本身不可重入。

## D21. lsctl 自带 `Backend` 接口，不复用 client 的 `Source`

**决策**：lsctl 定义自己的 `Backend` 接口（get / list / set / delete / history / rollback / migrate），HTTP 与 DB 各一个实现。

**理由**

第一反应是复用 `client.Source`——同样是"两种后端"。但 `Source` 只有 `Poll`：它是只读的、prefix 范围的、面向长轮询的。写入、历史、回滚在它上面一个都表达不了，硬套只会得到一个大部分方法都 panic 的接口。

两个接口服务的也是不同的东西。`Source` 要的是"变更感知"，热路径、要快、要能挂住；`Backend` 要的是"完整的管理操作"，一次性、要全。把它们塞进一个接口，两边的约束会互相拖累。

**否决的备选**：让 lsctl 直接依赖 `store.Store` 并给 HTTP 写个适配器。`store.Store` 的签名带 `store.Format`、`store.Result` 这些持久化层类型，HTTP 适配器得来回翻译；而 `api` 包里本来就有一套两端共用的线路类型，用它更直接。

**后果**：多一个接口。作为补偿，`Backend` 的两个实现由一整组双后端对拍测试守着（同一份数据、同一条命令，输出必须逐字节相同）。

## D22. not-found 独占退出码 4

**决策**：配置不存在时 lsctl 退出码为 4，其余错误一律 1。两个后端的 404 / `store.ErrNotFound` 都归一到同一个哨兵 `errNotFound`。

**理由**

`lsctl get k || 创建它` 是这类工具最常见的脚本用法。若"不存在"与"服务端 500"共用退出码 1，一次数据库抖动就会让脚本以为配置不存在，进而覆盖掉线上的值。这类事故安静、难查，且发生在故障期间——最不该再叠一层的时候。

选 4 而不是 2：2 在很多工具里是"用法错误"（cobra 的参数校验失败也走通用错误路径），留给它更稳妥。

**否决的备选**：加 `--exists` 之类的子命令做存在性判断。多一个命令，而退出码本来就是 shell 里表达这件事的方式。

**后果**：两个后端的错误映射必须保持同步。DB 后端为此专门把"历史为空"也映射成 not-found，以对齐服务端返回 404 的行为——有测试守着。

## D23. 手写 LCS diff，不引入 diff 库

**决策**：`cmd/lsctl/diff.go` 自己实现逐行 unified diff：剥公共前后缀，再做 LCS 回溯，超过规模上限退化成整段删+整段加。

**理由**

候选库都不合适：`go-difflib` 已归档，`sergi/go-diff` 是字符级的（配置 diff 要的是行级），其余多是重量级工具链的一部分。而这里要的东西很小——只用来看配置改了哪几行，不需要 myers 的最优性，也不需要词级高亮。

规模上限是必需的：LCS 是 O(n·m) 时空，两份 1 MiB 的配置各约 3 万行，表格就是 9 亿个格子。剥完公共前后缀后真实改动通常只剩几行，超限只在两份内容完全无关时才发生，那时"整段删+整段加"本来也是对的读法。

**否决的备选**：调外部 `diff(1)`。要落两个临时文件，Windows 上没有，且输出格式随实现漂移。

**后果**：约 150 行自维护代码。`unifiedDiff` 以"是否产生 hunk"判定有无差异，而不是先比较原文——`splitLines` 会吃掉结尾换行，只差一个换行的两份内容按行看是相同的，若按原文判定就会输出一个没有内容的空壳头部。

## D24. lsctl 的后端在进程级打开与关闭，不在子命令级

**决策**：后端缓存在 `root` 上，`main` 执行完命令后统一 `close()`；子命令只负责确保它已打开。

**理由**

最初写成子命令里 `defer be.Close()`，因为一次 CLI 调用只跑一条命令，看起来等价。测试立刻证伪了：测试要在同一个后端上连跑 set → get → history 来验证往返，第一条命令就把连接关了。

而这不只是测试的问题——它暴露了"谁拥有这个连接"没想清楚。后端的生命周期跟着 `root` 走，关闭就该在 `root` 消亡处，也就是 `main` 里。

**后果**：`newRootCmd` 返回 `(*cobra.Command, *root)` 而不只是命令。`dbBackend.Close` 对 `db == nil` 宽容，以支持"连接不归本后端所有"的场景（测试里就是这样）。

## D25. `-o json` 的输出一律走具名结构体，不用 `map[string]any`

**决策**：lsctl 每种 JSON 输出都定义一个结构体（`listOutput`、`historyOutput`、`diffOutput`、`dryRunOutput`、`writeOutput`），`emitJSON` 只接结构体。

**理由**

`encoding/json/v2` 默认不对 map 的键排序——这是它相对 v1 的一处行为变化，为性能而做。实测同一个 map 连续序列化，键顺序每次都不同。

后果是 `lsctl list -o json` 跑两次会给出不同的字节序列。把输出存成黄金文件、或在 CI 里 diff 两次调用的结果，都会随机失败。这个 bug 第一次暴露是在双后端对拍测试上：两个后端读同一份数据、输出却不相等，看起来像后端不一致，实际是序列化顺序在抖。

**否决的备选**：给 `emitJSON` 加 `jsonv2.Deterministic(true)`。能解决排序，但键顺序会变成字母序——`count` 排在 `configs` 前面，读起来别扭；而且它把"输出格式是什么"这件事藏进了一个序列化选项里，结构体则把它写在类型上。

**后果**：加一种输出就要加一个结构体。字段顺序即输出顺序，改动它是破坏性变更。有测试连续序列化 50 次断言字节一致。

## D26. bubbletea 模型用指针接收者，测试直接驱动 `Update`

**决策**：`Init` / `Update` / `View` 都挂在 `*uiModel` 上；测试同步调用 `Update`、递归执行它返回的 `tea.Cmd`，不引入 `teatest`，也不起伪终端。

**理由**

bubbletea 的例子多用值接收者，`Update` 返回改过的副本。这里不行：`loadKeys` / `loadDetail` 要在返回命令之前先 `keysSeq++`，序号涨在方法内部。值接收者下这个自增落在副本上，而返回给 runtime 的又是另一份——序号永远不涨，D27 的过期丢弃就整个失效，且失效得很安静。

测试这边，model 本身就是个纯函数：给一条消息，拿到新状态和一批命令。把命令跑掉、把产出的消息喂回去，就完整复现了 runtime 在做的事，而且是同步的——没有 sleep，没有 flake。

**否决的备选**：`teatest`。它测的是"终端上最终显示成什么"，这里更需要测的是状态迁移；它还要等输出稳定，把每个用例的耗时抬到百毫秒量级。

**后果**：约 30 个用例连 `-race` 跑在 4 秒内。测试自己实现 `dispatch`：执行命令、喂回消息、递归，并对 `tea.BatchMsg` 拆包；递归深度超过 20 判定为"消息链没有收敛"并失败，防的是自己触发自己的命令。渲染路径由另一组用例覆盖，断言每一行的显示宽度精确等于终端宽度。

## D27. 后端响应按单调序号丢弃过期结果

**决策**：`keysSeq` 与 `detailSeq` 两个计数器，发请求时自增并把当时的值写进消息；消息回来时序号对不上就丢掉。

**理由**

按住 `j` 从上往下扫 key 列表，每停一格发一次详情请求。这些请求并发在飞，返回顺序不保证——光标已经在第 5 个 key 上时，第 2 个 key 的响应才回来。没有丢弃机制的话，值栏的内容和光标指的 key 就对不上，而这种错位不会有任何提示。

用序号而不是"比较 key 是否相等"：在同一个 key 上按两次 `r`，两次响应的 key 都对得上，仍然需要丢掉先回来的那个。

两个计数器而不是一个：keys 的装载和 detail 的装载是两条独立的时间线，共用一个计数器会让任何一次列表刷新连带作废正在飞的详情请求。

**否决的备选**：每次请求带一个 `context.CancelFunc`，切换时取消上一个。能省掉序号，但取消是尽力而为——请求可能已经完成、消息已经进了队列，取消赶不上。丢弃发生在消费端，没有这个竞态。

**后果**：`Update` 里两处 `if msg.seq != m.xxxSeq { return m, nil }`。这两行由 `TestStaleDetailResponseIsDiscarded` / `TestStaleKeysResponseIsDiscarded` 守住，删掉任一行都会立刻变红。同一条推理也管着编辑：`$EDITOR` 退出后若选中项已变，这次编辑作废——那里用 key 判定而非序号，因为编辑是用户显式发起的，中途换 key 属于误操作而不是乱序。

## D28. 框线手写，lipgloss 只用来上色

**决策**：三栏的边框（`┌ keys ───┐`）用字符串拼；lipgloss 只负责给拼好的字符串套颜色。

**理由**

lipgloss 的 `Border` 画不了带标题的框——它只能画四条素边，没有"在顶边嵌一段文字"的位置。先让它画完再往里塞标题也不行：上过色的顶边是一串带 ANSI 转义的字符，按字节切会切在转义序列中间。

留着 lipgloss 是因为它做了一件手写不划算的事：识别终端能力。`NO_COLOR`、`TERM=dumb`、只支持 16 色的终端，它都会把颜色降级或直接去掉。自己写这套要连着 termenv 一起抄。

**否决的备选**：颜色也自己写死 ANSI 码。省一个依赖，但在不支持颜色的终端上会把 `\x1b[38;5;39m` 原样打成可见文本。

**后果**：`box()` 约 20 行，并带来一条必须遵守的顺序——文本先补齐宽度、再上色。反过来做，ANSI 转义会被算进显示宽度，三栏立刻错位。`uiLine` 就是为强制这个顺序而存在的：它只携带纯文本和一个 `lipgloss.Style`，样式要等 `box()` 补完宽度之后才施加。

另外 `runewidth.Truncate` 在宽字符跨过边界时会少给一列（请求 4 列、返回宽度 3），所以截断之后必须再补一次空格。这个 bug 是被"终端宽度取奇数"的用例逼出来的——只测偶数宽度时它一直藏着。

## D29. 编辑与回滚收敛到同一条确认路径

**决策**：两者都产出一个 `pending`，渲染成 diff 覆盖层，按 `y` 才写入；覆盖层里一并显示等价的非交互命令。`enter` 只在 history 栏触发回滚。

**理由**

一开始编辑和回滚是两套流程，写到一半发现形状完全一样：算出"要改成什么"、给用户看 diff、确认后调一次写接口。差别只在调 `Set` 还是 `Rollback`，以及状态行的措辞。合成一个 `pending` 之后确认逻辑只剩一份，`y` / `n` 的处理也不必分叉。

等价命令显示在覆盖层里，是 DESIGN §9.3 约束 2 的可见形式。约束本身只要求"存在等价命令"，但存在而用户找不到，等于不存在。摆在确认框上，用户看完 diff 顺手就能把那行抄进 CI/CD。

`enter` 的分工是安全考虑：把回滚绑在一个到处都能按的键上，光标恰好停在 history 栏时的一次误按就发出去了。左 / 中栏的 `enter` 改成"跳到 history 栏"——语义上是"钻进去看"，也恰好是回滚前必经的一步。

**否决的备选**：回滚也强制先按 `d` 看 diff。多一步，但回滚的目标版本就在光标上、diff 本来就在确认框里，强制两步只是把同一份信息看两遍。

**后果**：集成测试直接断言 `pend.equiv` 的字符串就是被执行的那条命令——同一份数据，TUI 回滚一次、`lsctl rollback` 回滚一次，结果必须相等。这是约束 2 唯一可执行的检验方式。退出 TUI 后本次会话的写入重播到 stderr：状态行随退出一起消失了，而事后最常被问的就是"我刚才到底改了什么"。

## D30. 配置值渲染前剥掉控制字符

**决策**：`stripControl` 去掉除制表符外的全部 C0 控制字符与 DEL，再送去渲染。

**理由**

配置值是用户写进数据库的任意字符串。一段 `\x1b[2J` 打到终端上会清屏，`\x1b[10;1H` 会挪光标，更长的序列能改标题栏、能重置终端。TUI 的整个布局靠精确的字符位置拼出来，任何一个逃逸出去的转义序列都会把后续画面搞乱——而且乱的样子看起来像是渲染代码有 bug。

剥掉而不是转义：这里不需要还原用户到底写了什么。值的权威副本在数据库里，`lsctl get` 拿得到原文；TUI 只要保证"看得见、且不会被内容操纵"。

制表符留着，因为它在配置里是有意义的缩进，交给 `fit()` 展开成四个空格。

**否决的备选**：把 ESC 换成可见的 `␛`。信息更全，但一段被打断的转义序列渲染出来是一串噪音，占的宽度还不确定。

**后果**：值里的 `\x1b[6n` 会显示成 `[6n`——ESC 没了，剩下的是普通文本。这是有意的：目标是让序列失效，不是抹掉用户的内容。测试断言的正是这个形态。
